## 📝 Documentation Standards

### **For Internal Developers**

When creating or updating documentation:

#### **1. Choose the Right Location**
- **Root directory:** Core development docs
- **docs/:** Organizational and index docs
- **docs/client/:** Client-facing docs
- **sample-app/:** Sample app specific docs
- **In-code:** Technical architecture docs

#### **2. Use Consistent Formatting**
- **Markdown (.md)** format
- **Clear headings** with emojis for visual navigation
- **Tables** for structured data
- **Code blocks** with syntax highlighting
- **Links** between related documents

#### **3. Keep Documentation Updated**
- Update when changing functionality
- Create release notes for each version
- Archive old deployment summaries
- Review during release process

#### **4. Target Your Audience**
- **Internal docs:** Assume SDK development knowledge
- **Client docs:** Assume Android development knowledge
- **Quick starts:** Assume minimal knowledge, focus on speed

## 🔄 Documentation Workflow

### **When Making Code Changes**
1. **Update relevant docs** if behavior changes
2. **Add to changelog** if user-facing
3. **Update code comments** for complex logic

### **When Releasing**
1. **Create release notes:** `docs/client/RELEASE_NOTES_vX.X.XX.md`
2. **Create deployment summary:** `docs/client/DEPLOYMENT_SUMMARY_vX.X.XX.md`
3. **Update README.md** with new version
4. **Update DEVELOPER_README.md** version history

### **When Adding Features**
1. **Document in code** with KDoc comments
2. **Update sample app** to demonstrate feature
3. **Update guides** if client-facing
4. **Add to testing checklist**
